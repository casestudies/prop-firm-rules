# Verification methodology

This document describes how the records in this repository were built and
checked. It applies to every field in `firms/showcase/` and to the coverage
facts in `firms/metadata.json`.

## 1. What "verified" means here

Every value is transcribed from the named firm's own published documentation —
not from a forum post, a review site, a leaderboard, or a competitor's summary.
Each record carries a structured provenance entry alongside its values: for the
fields it covers, a source URL, the exact supporting quote, the date it was
retrieved, and a confidence label describing how directly the firm's own words
support the stored value (`sourced`, `derived`, `reconciled`, or `ambiguous` —
defined in `SCHEMA.md`). Coverage is not uniform field-by-field: a figure that is
exact arithmetic on an already-cited percentage carries its source through that
percentage rather than as a second copy of the same quote, and a handful of
structural fields still carry a thinner citation than the rest. It is real and
checkable either way — every showcase record's `provenance` block can be opened
and compared, field by field, against the cited URL.

## 2. Where the firm's own documentation does not settle it

Firms sometimes describe the same rule two different ways, or publish a value
that admits more than one reading. When that happens, it is recorded rather than
guessed past: an ambiguous field lists every candidate reading, states which one
is modeled, and carries the reasoning for that choice in full — see the
`ambiguities[]` entries inside any showcase record. The default stance is
conservative: the reading that makes passing harder is the one modeled, so a
disclosed ambiguity never quietly flatters an outcome in either direction.

## 3. How a value gets checked twice

Beyond the first read, records are periodically re-verified with a two-pass
blind method: the value is re-derived independently, without looking at the
stored value first, and only then compared against what is on record. Where the
two passes agree, the field is confirmed. Where they disagree — including cases
where a firm's own page contradicts itself between two explanations of the same
rule — the disagreement is written down, not silently resolved toward whichever
direction is more convenient. Every recheck is dated and named in a record's
`rechecks[]` array, method included.

## 4. Field-level citability, not a single per-firm stamp

A firm is not "verified" or "not verified" as a single unit — each FIELD carries
its own confidence label, source, and retrieval date, and a firm's overall
"last checked" date (in `firms/metadata.json`) is the newest of those field-level
dates: the later of its most recent independent recheck and its most recent
retrieval. That is a real, computed maximum over dated evidence, not a rounded
or asserted figure.

## 5. Golden vectors

Where a firm publishes a worked example — a concrete sequence of trades with a
stated pass/fail outcome — that example becomes a golden vector: an expected
result taken directly from the firm's own materials, never generated by running
any simulator against itself (which would be circular and prove nothing).
`firms/metadata.json`'s `hasGoldenVector` flag says, per firm, whether such an
example exists on record. The vectors themselves are not published in this
repository — they are an internal correctness check, not a dataset field.

## 6. What this repository is, and is not

This repository is a schema definition, a verification methodology, five
firms shown in full detail, and lightweight coverage metadata for the rest of
the firms this corpus tracks. It is not the working corpus, not an engine, and
not investment, trading, or legal advice — it publishes no pass rates, rankings,
or comparative claims about any named firm; a firm's rules are facts about a
published document, not a judgment about the firm.

This snapshot is dated 2026-09-10. The complete, current dataset — every
tracked firm, every account size, every cited field — lives inside the free
simulator at https://propsurvival.com/.

## 7. Reproducibility

This repository is generated deterministically from a larger, private working
corpus by one script; regenerating it from the same corpus state reproduces it
byte-for-byte. It carries no field this script cannot trace to a specific
source file.
